# The pipeline lives in the server fork

The build, snapshot, candidate, sync and commit-lint workflows are `ionos-*.yml` files in the server fork, kept as `IONOS(ci)` commits in the patch series, and the fork's default branch is the live line's `ionos-dev-v<nn>`. A snapshot then freezes its own pipeline, so an old release rebuilds with exactly the workflows it shipped with. We considered keeping the workflows in the flavors repo, which leaves the fork closer to upstream but cannot freeze the pipeline with the release and still needs a token with write access to the fork.

The workflows that push branches (candidates, snapshots, pin proposals) use a token stored as the repository secret `IONOS_SYNC_TOKEN`: a fine-grained personal access token limited to the fork, with the `workflow` scope (a GitHub App is the later upgrade). The default workflow token is not enough, because GitHub does not let it create or update files under `.github/workflows`, and the patch series, and so every candidate rebased from it, contains workflow files. It is a same-repo token, not a cross-repo one. Unlike the default token, pushes and pull requests made with it start other workflows, which is also why the commit-lint workflow runs on the pull requests the automation opens.

The costs: the default branch is not `master`, so it must be switched at cutover; upstream's own workflows exist in the fork and must be disabled through the Actions API by the sync job, because deleting them would conflict on every rebase; the workflow files are part of the series and are rebased with it; and the token belongs to a person and expires, so it needs an owner and a renewal date.
