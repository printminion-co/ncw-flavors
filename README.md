# ncw-flavors, line 33

Flavors, bases, themes and build tooling for stable line 33 of Nextcloud. The design lives on the `main`
branch of this repository (`docs/spec/`).

```
flavors/<name>/   flavor.yaml, config/NN-<name>.config.php
bases/<name>/     same structure, reused by flavors through `extends`
themes/<name>/   theme packages (lib/*.php, assets/**)
tools/            the build tooling (TypeScript on Node 24)
```

## Build an artifact

```
cd tools && npm ci
node src/cli.ts build --flavors .. --flavor flavor1 --tree <built server tree> \
  --line 33 --kind dev --build-number 812 --out <dir>
```

Prints the path of `ncw-<flavor>-v<base release>.<build number>.zip` to stdout, and the resolved flavor (see
below) to stderr for the build log. The artifact holds the server tree with the
flavor applied: shipped-apps lists generated from the app modes, removed apps pruned, only the active app folders,
the flavor's partial configs, the build number file, and a version file that reports channel `git` and the build
number as a fifth version element. The dev files are stripped (see "Dev files" below), which includes the install
flag file and the web updater. The same inputs give
byte-identical artifacts. Besides the server tree the artifact root holds `app-config.json`,
`app-config-special.json`, `removed-apps.json` and `version.json` (see below). The build needs `php` to read the
keys of the partial configs.

Partial config names are `NN-<name>.config.php`; see "Config and environment rules" for the numbers.

## See what a flavor resolves to

```
node src/cli.ts resolve --flavors .. --flavor flavor1
```

Prints the fully resolved flavor as YAML for review: the manifests in the order they were applied, the apps with
their modes, the app folders, the themes, the config files with the manifest each one comes from, and the
environment variables.

A flavor's bases are applied depth first in the listed order, then the flavor itself, and the last declaration wins
per app, per config file name and per environment variable. Themes and app folders are an ordered union. A base
reached through more than one path is applied once, where it is first reached. A cycle in `extends` is rejected
and the message names it.

## Check app version compatibility

```
node src/cli.ts check-compat --flavors .. --flavor flavor1 --tree <server checkout>
```

Every app that stays in the artifact (in `apps/` and the active app folders) must accept the server version of the
tree: the `min-version` and `max-version` of `<nextcloud>` in its `appinfo/info.xml` are compared only as far as
they are written, so `max-version="33"` accepts 33.0.9. A missing or malformed bound is an error; removed apps are
skipped. A failure exits with 2 and prints, to stderr, a GitHub Actions `::error file=...,title=App version
compatibility::` annotation and a readable line per app naming the app, both bounds and the server version.
`build` runs the same check on the source tree before assembling and on the assembled tree afterwards, for dev and
release builds alike.

## Config and environment rules

The build checks every flavor before it writes anything; a violation is an input error (exit 2, nothing written).

- Partial configs are named `NN-<name>.config.php`. A name without a two digit number is an input error. Numbers
  00 to 09 are reserved for files the tool generates (`00-apps-paths`) and are an input error in a base or a
  flavor. By convention bases use 10 to 49 and flavors 50 to 89; any other number (such as 90 to 99) is only a
  warning on stderr (`warning: config file X uses number NN, bases use 10-49 and flavors use 50-89`) and the build
  succeeds. Two different file names with the same number in one resolved flavor are an input error naming both
  files. A file with the same name in a nearer base or in the flavor replaces the earlier one, so a flavor can
  override a base file by name (and, having the same name, the same number); that replacement is not warned
  about. Nextcloud loads the files in name
  order, so the number is the order.
- Flavor and base configs may not set these keys, a fixed set: the deployment keys `dbtype`, `dbname`, `dbhost`,
  `dbport`, `dbuser`, `dbpassword`, `dbtableprefix`, `dbpersistent`, `dbdriveroptions`, `db.replica`,
  `objectstore`, `objectstore_multibucket`, `trusted_domains`, `instanceid`, `passwordsalt`, `secret`,
  `mail_sendmailmode`, `datadirectory` and every key that starts with `mail_smtp`; the keys Nextcloud writes
  itself, `version` and `installed`; and `apps_paths` (generated by the tool at 00). The keys are found by
  evaluating each partial config with `php`, so the build needs `php` installed whenever there is a partial
  config (it fails with a message if `php` cannot be run).
- Environment variables must be declared in a manifest (`env:` with `name`, `required`, `default`). A
  `getenv('NAME')` or `getenv("NAME")` in a partial config (found by a text scan) and a `${NAME}` in
  `app-config.json` must be declared, or the build fails. A declared variable nothing uses gives a
  `warning:` line on stderr.

### App config

A flavor or base may have `app-config.json` next to `flavor.yaml`:

```json
{
  "apps": { "files": { "max_chunk_size": 10485760, "old_key": null } },
  "special": [
    { "app": "ldap", "key": "bind_password", "value": "${LDAP_PASSWORD}", "sensitive": true },
    { "app": "files", "key": "limit", "value": "5", "type": "integer", "lazy": true }
  ]
}
```

`apps` is app to key to string or integer (null deletes the key), exactly what `occ config:import` accepts.
`special` holds what the import cannot set (`occ config:app:set --sensitive/--lazy/--type`); `type` is one of
string, integer, float, boolean, array, and a sensitive value must be a whole `${VAR}` placeholder, a literal
is an error. Bases apply first, the flavor last; the last declaration wins per app and key. A `system` section is
rejected. The same app and key may not be in both `apps` and `special`.

The artifact root gets `app-config.json` (`{"apps": ...}`, sorted, placeholders unresolved), `app-config-special.json`
(the merged `special` list, sorted by app and key) and `removed-apps.json` (sorted array of the vanilla apps the flavor
removes, that is only those in the `shippedApps` list of the tree's `core/shipped.json`; a removed app the tree
does not ship is not listed). Secrets are never written: only `${VAR}` placeholders.

## Validate an artifact

```
node src/cli.ts validate --flavors .. --flavor flavor1 --artifact <zip or unpacked directory>
```

Static checks of a produced artifact against the resolved flavor. Exit 0 when every rule passes; otherwise exit 2
with every violation on stderr, each naming the file or app. Warnings (an app without a mode in a `dev` artifact)
go to stderr and do not fail.

- Config: `config/` holds exactly the flavor's partial configs, the generated files (`00-apps-paths.config.php`,
  and `01-themes.config.php` when the flavor has themes; each must be present) and upstream's `config.sample.php`
  and `.htaccess`. Anything else is an unexpected file; a missing expected file is an error. Two different file
  names with the same number are an error naming both files.
- Apps: an app is a folder with `appinfo/info.xml` directly below `apps/` or an active app folder. A removed app
  that is present and a non-removed app of the flavor that is absent are errors. An app with no mode in the flavor
  is an error unless `version.json` says `kind` is `dev`, which makes it a warning.
- Shipped lists (`core/shipped.json`): a removed app is in none of the three lists; an `always` app is in
  `alwaysEnabled`; a `default` app is in `defaultEnabled` and not in `alwaysEnabled`; an `available` app is in
  neither; an added app (one not in the server's own `apps/`) is never in `shippedApps`.
- Forbidden entries: the dev files (see "Dev files" below).
- Version files: `version.json`, `.buildnumber` and `version.php` are present; `.buildnumber` is a positive
  integer equal to `build_number` in `version.json`; `version.php` sets the channel `git` and has the build number
  snippet exactly once. `flavor` in `version.json` equals `--flavor` (the error names both).

The artifact is the zip `build` wrote or the same tree unpacked; both give the same result.

### Dev files

`build` strips the dev files from the tree and `validate` forbids them; one definition (`tools/src/devfiles.ts`)
serves both. Dev files are: `.git`, `.github`, `.gitignore`, `.gitmodules` and `node_modules` at any depth (as a
file or a folder); `tests` and `test` folders below an app (`apps/<id>/...` or `<active app folder>/<id>/...`,
not elsewhere); the top-level folder `IONOS` (the flavors repository submodule of the server fork, which never
ships); `config/CAN_INSTALL`; and `updater/`.

## App modes and classification

Every app in the tree or in an active app folder needs a mode. An app without one is a warning on stderr in a `dev`
build and a failure in a `release` build. The same app id in two active app folders, or in one and the server tree
(`apps/<id>`), fails and names both locations (Nextcloud would load only one of them). Before the lists are written
the build checks that no removed app is left in any of them.

## Build metadata

Every artifact holds `version.json`, written by the build from inputs the pipeline supplies (the tool does not run
git itself). Pretty JSON, two-space indent, sorted keys, final newline; only these fields exist:
`flavor`, `base_release`, `build_number` (the integer given with `--build-number`), `kind` (`dev` or `release`), `snapshot_branch`, `release_number`, `scope`,
`server_commit`, `flavors_commit`, `apps` (app id to `commit` and `describe`) and `cached_builds` (app id to
`key` and `checksum`).

| Option | Meaning |
| --- | --- |
| `--snapshot-branch <name>`, `--release-number <n>`, `--scope <text>` | Required for kind `release`; optional for `dev`. A field whose option is not given is left out of the file. The release number is a positive integer, the scope is not empty. |
| `--server-commit <sha>`, `--flavors-commit <sha>` | Optional hex commit shas (7 to 64 digits); left out when not given. |
| `--app-pins <file.json>` | JSON object `{"<app id>": {"commit": "<sha>", "describe": "<git describe>"}}`. Both fields required, no others. |
| `--cache-keys <file.json>` | JSON object `{"<app id>": {"key": "<cache key>", "checksum": "<checksum>"}}`. Both fields required, no others. |

`apps` and `cached_builds` are `{}` when their option is not given. Bad input is rejected before anything is
written. A negative build number must be written `--build-number=-5` (the form `--build-number -5` is refused by the argument parser, also with exit 2).
Processing a tree whose version file already has the build number snippet does not append it a second time.

## Themes

A theme is a package `themes/<name>/` in the flavors root:

```
themes/<name>/lib/*.php     the theme class files
themes/<name>/mail/*.php    mail template classes (activated by the mail_template_class config, not registered)
themes/<name>/assets/**     everything else: CSS, images, fonts, translation and template overrides
```

Only files directly in `lib/` and `mail/` are classes; a nested file or folder below them is an input error naming it. A
theme's translation and template overrides live under `themes/<name>/assets/` and are copied to `themes/<name>/` in the artifact.

A flavor (or base) lists themes in its manifest (`themes: [acme]`, an ordered union over the bases) and may
enforce one with `enforce_theme: acme` (the last declaration wins; it must be one of the flavor's themes, and a
theme without a package folder is an input error). `ncw resolve` shows `themes` and `enforce_theme`.

The build copies each `lib/<Class>.php` to `lib/private/Ncw/Themes/<Class>.php`, each `mail/<Class>.php` to
`lib/private/Ncw/Mail/<Class>.php` and each asset to `themes/<name>/<path under assets>` in the artifact. Not to the
theming app: its autoloader is a classmap that never finds a class added to `apps/theming/lib`, while the server's `OC\`
namespace is loaded by PSR-4 from `lib/private`. The class name of a theme class is `OC\Ncw\Themes\<file name without
.php>`, and the theme name must equal the id the class returns; the tool cannot check that. `validate` checks that
every file of the theme packages is in the artifact with the same content. For a flavor with at
least one theme the build generates `config/01-themes.config.php` (number 01 is in the range reserved for generated
files, next to `00-apps-paths.config.php`):

```php
$CONFIG = ['ncw.themes' => ['OC\\Ncw\\Themes\\Acme'], 'enforce_theme' => 'acme'];
```

`enforce_theme` is left out when no theme is enforced. A flavor config may not set `ncw.themes` or `enforce_theme`.
The server setting `ncw.themes` is read by a generic patch in the server fork (`IONOS(branding): register the theme
classes listed in ncw.themes`); this tool only generates the config. The first theme package is `themes/ionos`
(its README says where the brand values are and where a logo and a favicon go).
